# Как ведётся работа над Lancible

Порядок принят 19 сентября 2026 года и действует по умолчанию для любой задачи
в этом репозитории. Отступать от него можно только если об этом попросили прямо.

## Круг работы

1. **Опрос.** Получив задачу, сначала уточняю, чего именно от неё ждут:
   спрашиваю про развилки, которые меняют результат, а не про то, что видно в
   коде или решается очевидным умолчанием. Очевидное решаю сам и называю
   принятое решение в ответе.
2. **Сначала граф.** Прежде чем искать по коду, спрашиваю graphify:
   `graphify query`, `path`, `explain`, `affected`. Он отдаёт подграф по теме,
   а не простыню совпадений — см. ниже.
3. **Работа.** Только после опроса.
4. **Сначала существующее.** Перед тем как заводить новый компонент, стиль или
   токен, ищу готовый и беру его. Новое появляется, когда готового правда нет
   или когда об этом попросили. Частные случаи, на которых уже обжигались:
   выпадающие списки — только свой стиль (`.ctx-menu`), никаких системных
   `<select>`; модалки центруются через общий механизм, а не через отдельные
   правила; шапка и подвал лендинга одни и те же на всех его страницах.
   **Визуал — по карте `DESIGN.md`**: у каждой поверхности один источник
   токенов (десктоп с вебом — `styles.css`, телефон — `theme.js`, лендинг —
   `landing.css`); цвет — только токеном; общая деталь — в общем месте, а
   экран подправляет её селектором со своим классом; из JS — только
   координаты, размеры и данные пользователя. Сторожит
   `tests/unit/visual-rules.test.js`.
5. **Проверка кодом, а не руками.** Замер, сделанный один раз в консоли,
   живёт ровно один день. Поэтому проверка пишется тестом и попадает в набор:
   размеры через `getBoundingClientRect`, стили через `getComputedStyle`,
   адреса через код ответа — всё это утверждения в `tests/`, а не разовые
   прогоны. Руками меряю только то, чего ещё нет чем закрыть, и сразу после
   этого закрываю. Скриншот — доказательство для человека, а не способ
   убедиться самому. Пока идёт работа, за набором следит `npm run watch`.
   Веб и лендинг поднимаются локально (`npm run serve:web`,
   `npm run serve:landing`).
6. **Логи.** Каждая ошибка, нестыковка и правка попадают в журнал — см. ниже.
7. **На проверку.** Готовое отдаю с описанием того, что изменилось и чем это
   подтверждено. Статус задачи в журнале перевожу в `review`.
8. **Круг правок.** Есть замечания — возвращаемся к пункту 1 по каждому из них.
   Номер круга растёт, он виден в журнале.
9. **Деплой только по команде.** Пуш в `main` разворачивает и веб, и лендинг,
   поэтому без прямого «деплой» ничего никуда не уходит. Коммиты локальные —
   можно и нужно. Перед пушем — `npm run site:refresh`: он выкладывает
   свежий граф кода на `/graph` (с проверкой на секреты) и пересчитывает
   числа о коде на `/graph` и `/architecture`; результат — отдельным коммитом.
10. **Запись в блог.** После деплоя — новая запись в `landing/blog-posts.js`,
   если пользователю есть что заметить. Правила отбора описаны в шапке файла:
   мелкие правки туда не идут, для них есть журнал.

Пункты 9 и 10 с 10 октября 2026 выполняет Publish Agent — см. «Команда
агентов» ниже.

## Команда агентов

Принято 10 октября 2026. Над проектом работают параллельные сессии Claude,
у каждой своя зона. Пользователь говорит только с Product Manager. Всё
остальное общение идёт между сессиями: сообщения по имени сессии и задачи в
журнале.

Общие правила для всех ролей:

- **Тесты к правке пишет автор правки, в своей ветке.** Это не залезание в зону
  тестировщика. Тестировщик ведёт приёмку, регрессию и инфраструктуру тестов и
  не меняет продуктовый код.
- **Общие документы.** `DESIGN.md` и `ARCHITECTURE.md` каждый правит в своём
  разделе. Сам этот регламент меняется только по слову пользователя.
- **Иконки и графика** — только через Icons and Graphics.
- **Цвета (токены)** остаются за своей поверхностью: см. `DESIGN.md`.

### Как ходят задачи

1. **PM ставит задачу.** PM заводит задачу в журнале (`task.id` вида
   `ГГГГ-ММ-ДД-о-чём`, в `title` — владелец в скобках) и пишет исполнителю
   сообщением с этим id.
2. **Исполнитель работает.** Он ведёт журнал по тому же id и работает в
   ветке `<префикс>/<о-чём>`. Нужна чужая зона — пишет её владельцу.
3. **Разработчик и тестировщик правят напрямую.** Тестировщик шлёт замечания
   разработчику, разработчик возвращает исправленное тестировщику. PM видит
   это в журнале.
4. **Готово.** Ветка уходит на GitHub (`git push origin <ветка>`). Это не
   деплой: production берётся только из `main`. Исполнитель сообщает PM и
   Publish имя ветки и чем проверено; статус в журнале — `review`.
5. **Деплой.** Пользователь говорит «деплой» → PM поручает Publish Agent.
   Publish:
   - просит Legal Manager проверить релиз;
   - смотрит дифф каждой ветки;
   - сливает ветки в `main`: сначала Core, потом остальные;
   - гоняет полный `npm test`;
   - делает `npm run site:refresh` отдельным коммитом;
   - пушит, ставит теги, пишет запись в блог;
   - переводит задачи в журнале в `deployed`.

### Файлы-магниты и общие ресурсы

- **Пересобираемые файлы.** `tests/unit/graph-orphans.baseline.json`,
  `landing/graph*.html` и числа `/architecture` при слиянии руками не
  сливаются: Publish пересобирает их (`npm run graph:baseline`,
  `npm run site:refresh`). Копии ядра в `mobile/src/core/` обновляет только
  Core (`scripts/sync-mobile-core.js`). Сборку редактора — только Web/Desktop
  (`npm run build:editor`).
- **Эмулятор Android и Metro на 8081 — один на всех.** Mobile и Testing Mobile
  договариваются, кто занимает их сейчас.
- **Порты браузерных прогонов** (`tests/ports.js`) общие для всех копий, а
  Playwright переиспользует уже поднятый сервер. Два прогона из разных копий
  одновременно проверят чужой код. Пока порты не стали свои для каждой копии,
  браузерные наборы из двух копий сразу не гоняем.
- **Режим разрешений у всех сессий один.** Иначе каждое сообщение между ними
  ждёт подтверждения пользователя.

## Журнал работы

Живёт в Supabase и показывается на `https://lancible.vercel.app/logs`. Страница
читает базу при каждой загрузке, поэтому запись видна сразу и деплой для этого
не нужен — это и есть причина, по которой журнал не лежит файлом в репозитории,
в отличие от блога.

Запись — одной командой на задачу:

```bash
node scripts/worklog.js <<'EOF'
{
  "task": { "id": "2026-09-19-logs-page", "title": "Как её сформулировал пользователь",
            "status": "review", "summary": "Одно предложение: что вышло" },
  "events": [
    { "kind": "error", "title": "Что сломалось", "detail": "Почему именно" },
    { "kind": "fix",   "title": "Чем починено" }
  ]
}
EOF
```

`task.id` — слаг вида `ГГГГ-ММ-ДД-о-чём`, он же ключ: повторная запись с тем же
id дополняет задачу, а не заводит новую.

Виды событий: `request` (правка или уточнение от пользователя), `change`
(что сделано), `error` (что сломалось и почему), `fix` (чем починено), `check`
(что проверено и каким замером), `deploy` (что и когда уехало).

Статусы задачи: `in_progress` → `review` → `accepted` → `deployed`.

Писать может только служебный ключ `SUPABASE_SERVICE_ROLE_KEY` (переменная
окружения или `.env.local` в корне). Если ключа нет или база недоступна, запись
не теряется: она ложится в `logs/pending.jsonl`, и `node scripts/worklog.js
flush` досылает очередь. Схема таблиц и правила доступа — `supabase/logs.sql`.

## Автотесты

Гоняются сами, три раза на разной дистанции:

- **пока идёт работа** — `npm run watch`: следит за файлами и прогоняет ровно
  те слои, которых коснулась правка. Сохранил файл — через секунду знаешь.
- **перед каждым коммитом** — крюк: обновляет граф кода и гоняет `test:fast`.
  Секунды. Включается сам на `npm install`; разово обойти — `git commit
  --no-verify`.
- **на каждый push и pull request** — GitHub, всё целиком, пятью
  параллельными работами (`.github/workflows/test.yml`); одна из них только
  собирает бандл телефона.

```bash
npm run watch        # сторож: гоняет затронутое, пока идёт работа
npm run watch -- --fast   # он же, но без браузерных слоёв

npm test             # всё целиком
npm run test:fast    # то, что гоняет крюк: юниты и генератор таблиц
npm run test:unit    # чистая логика и правила в исходниках, без браузера
npm run test:mobile  # экраны и стор телефона, jest-expo
npm run check:mobile-build  # собирает ли Metro бандл Android
npm run test:e2e     # веб-версия в браузере, Playwright
npm run test:landing # лендинг в браузере
npm run test:visual  # снимки с эталоном
npm run test:backend # права доступа к базе
npm run smoke        # десктоп целиком, в Electron без окна
```

**Пять слоёв, и у каждого своя работа.**

`tests/unit/` — всё, что видно в исходниках и не требует ни браузера, ни сети.
Чистая логика из `src/renderer/core/` (форматирование, деньги, статусы,
миграция, переводы) и правила, которые раньше держались на внимании:
`ui-rules.test.js` — системных `<select>` нет, все модалки центруются одним
правилом; `landing.test.js` — шапка и подвал одинаковы на всех страницах
лендинга, ссылки ведут куда обещают, служебные страницы закрыты от
поисковиков; `architecture.test.js` — схема на `/architecture` и
`ARCHITECTURE.md` называют правильное число файлов ядра и работ в CI, а в
выложенном графе нет секретов; `visual-rules.test.js` — цвета только из токенов своей
поверхности, нынешние отступления списком-храповиком; `graph-dead-code.test.js` — в графе не появилось новых символов,
которых никто не зовёт. Встроенный в Node тест-раннер, ноль зависимостей,
доли секунды. Сюда же самый важный тест приложения — повторный прогон
миграции не должен ничего менять.

`mobile/tests/` — экраны и стор телефона: jest + jest-expo +
`@testing-library/react-native`, прогон живёт в `mobile/` со своими
зависимостями. Правило отбора: проверяем не правило, а его применение.
Само правило (например, что делает галочка «выполнено») лежит в ядре и уже
закрыто юнитами; здесь — что телефон его зовёт, а не пересказывает своими
словами. Подмены нативных модулей — в `mobile/jest.setup.js`, и только те, у
которых в Node нет нативной части: хранилище и уведомления.

**Сборка телефона** — не слой тестов, а проверка поверх них. jest гоняет код
в Node, а бандл для APK собирает Metro, и понимают они разное: 6 октября 2026
сборка падала на `require` с вычисляемым путём при зелёном наборе.
`npm run check:mobile-build` собирает бандл Android (`expo export` во
временную папку, с байткодом Hermes) и падает, если Metro его не собрал. Её
гоняют сторож — на правку в `mobile/`, кроме тестов, — `npm test` и
отдельная работа «Сборка телефона» в GitHub. В крюк не входит: 10–20 секунд.

`tests/e2e/` — настоящий браузер поверх собранного `web/`. Сервер поднимается
сам, данные вкладки чистятся перед каждым тестом. Время прибито
(`tests/e2e/clock.js`), иначе часть тестов зависит от дня недели.
`layout.spec.js` меряет вёрстку: нет горизонтальной прокрутки на 1280 и 375,
модалки стоят по центру, меню не уезжает за край.

`tests/landing/` — лендинг в браузере: высоты шапки и подвала совпадают на
всех страницах, ничего не вылезает за поле, порог сужения шапки проверяется с
обеих сторон, служебные адреса отдают 200, граф на `/graph` рисуется, подписи
схемы на `/architecture` не наезжают друг на друга.

`tests/visual/` — снимки с эталоном. Эталон привязан к системе: Chromium на
Windows и на Linux рисует текст по-разному. Нет эталона для этой системы —
тест пропускается **громко**, с причиной и командой
`npm run test:visual:update`. Снимаются элементы, а не страницы целиком:
первая версия весила 14 МБ, и журнал в ней ломался от каждой новой записи,
потому что читает базу. Снимок — не доказательство «ничего не сдвинулось»:
пиксели плавают даже между двумя прогонами без правок (сглаживание,
анимации), отсюда допуск 1%, а пересъёмка перезаписывает только эталоны,
вышедшие за допуск, — мелкая настоящая правка эталон не обновит. Точное
доказательство вида — сравнение вычисленных стилей до и после.

`tests/backend/` — права доступа к базе. Своего сервера у нас нет, ключ `anon`
открыт, и от чужих данных отделяют только политики. Запись проверяется
строкой, которая заведомо нарушает внешний ключ: смотрим на код ошибки, где
`42501` — отказ политики (так и надо), а `23503` — политика пропустила.

**Почему логика лежит в `src/renderer/core/`.** `app.js` — один большой файл,
где расчёт и отрисовка перемешаны, и юнит-тест к нему не подступиться. Чистые
функции вынесены в отдельные файлы, которые читаются и браузером, и Node;
в `app.js` остались обёртки с прежними именами, подставляющие `state`. Новую
чистую логику пишем сразу туда — и сразу с тестом. Файлы из `core/`
копируются в `web/` целиком на сборке, отдельной строкой их регистрировать не
нужно, но подключить `<script>` в обоих `index.html` — нужно. Перевод строки
для `core/` прибит к LF в `.gitattributes`: копии в `mobile/src/core/`
сравниваются побайтно, и выгрузка с CRLF ломала бы сравнение невидимо.

**Известные недоработки** помечены в наборе, а не спрятаны: `{ todo: ... }` в
Node и `test.fail(...)` в Playwright. Такой тест виден в отчёте, но не красит
сборку красным — пока не решено, чинить ли.

## Что ещё стоит помнить

- Десктоп собирается под Windows и macOS вместе и должен оставаться одинаковым.
- Редактор текста — `src/editor/` (ProseMirror). После правки в нём —
  `npm run build:editor`: сборка (`src/renderer/editor.js` и
  `mobile/src/editor/editorBundle.js`) закоммичена, Vercel и EAS её не
  собирают. Отставшую сборку ловит `tests/unit/editor-bundle.test.js`.
- Картинки редактора уходят в облако только после разового
  `supabase/storage.sql` в SQL Editor; до этого они живут на устройстве.
- `web/index.html` написан руками, а стили тянет общие с десктопом — после
  правки разметки в `src/renderer/index.html` его нужно править следом.
- Лендинг и веб деплоятся из `main` автоматически одним проектом Vercel: веб
  собирается внутрь лендинга по адресу `/app` (`scripts/build-landing-app.js`,
  команды — в `landing/vercel.json`). Установщики — по тегу `v*`, APK — по тегу
  `mobile-v*`.
- **Один адрес — `lancible.vercel.app`**, всё остальное открывается от него.
  Отдельных адресов не заводим; исключения — будущая админ-панель и служебные
  функции без страниц. Сторожит `tests/unit/landing.test.js`.

## graphify

Граф кода проекта лежит в `graphify-out/` (в репозиторий не коммитится —
производный артефакт на 4 МБ, пересобирается за шесть секунд). В нём узлы,
связи между файлами и разбиение на сообщества.

**Граф — первая остановка, а не последняя.** Прежде чем искать по коду
грепом, спрашиваем граф: он отдаёт подграф по теме, а не простыню совпадений.
Хуки в `.claude/settings.json` об этом напоминают перед каждым поиском и
чтением.

```bash
graphify query "<вопрос>"      # подграф по вопросу
graphify path "<А>" "<Б>"      # как одно связано с другим
graphify explain "<понятие>"   # узел и его соседи простыми словами
graphify affected "<Х>"        # кого заденет правка Х
graphify god-nodes             # самые связанные узлы
npm run graph:update           # пересобрать граф (AST, без оплаты)
npm run graph:baseline         # переснять список узлов без входящих рёбер
npm run site:refresh           # выложить граф на /graph — перед выкатом
```

Граф можно смотреть и в браузере: `lancible.vercel.app/graph`. Страница
служебная, как `/logs` и `/architecture`: ссылок на неё нет, поисковикам
закрыта. Обновляется не сама, а `npm run site:refresh` перед выкатом.

`graphify-out/GRAPH_REPORT.md` читаем только для общего обзора устройства,
когда query/path/explain не дали достаточно.

**CSS граф не разбирает** — только JS. По стилям первая остановка —
`DESIGN.md`: где у какой поверхности токены, общие детали и экраны.

**Граф обновляется сам** — крюком перед каждым коммитом, до прогона тестов:
по нему работает проверка на мёртвый код, и по устаревшему графу она сказала
бы неправду. Если graphify не установлен, коммит из-за этого не
останавливается, а проверка пропускается с объяснением.

**Мёртвый код.** `tests/unit/graph-dead-code.test.js` следит за узлами, в
которые не ведёт ни одно ребро использования. Нулём этот список не бывает:
точка входа не имеет входящих рёбер по определению, а разбор по именам не
видит обработчик, переданный в JSX как `onPress={onAdd}`. Поэтому сравнение
идёт со снимком `tests/unit/graph-orphans.baseline.json`: появился новый —
иди посмотри, что это; вычистил код — перепиши снимок `npm run
graph:baseline` и увидь в diff, что именно ушло.
