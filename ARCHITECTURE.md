# Как устроен Lancible

Одна модель данных на четыре поверхности: десктоп, веб, телефон и лендинг.
Здесь — что где лежит, что между поверхностями общее, что продублировано и
чем за это платим; в конце — список работ (он вытекает из устройства выше).
Где у поверхностей цвета, шрифты, детали и экраны — `DESIGN.md`.

То же с картинками — раздел «Устройство» админки
(`admin/content/architecture.html`), рядом — «Граф кода»
(`admin/graph/graph.json`). До 23 октября 2026 это были служебные страницы
лендинга `/architecture` и `/graph`; теперь их там нет. Числа там и здесь не
расходятся: редкие (файлы ядра, сколько из них у телефона, работы CI)
сторожит `tests/unit/architecture.test.js`, частые (строки и функции
`app.js`, граф) пересчитывает `npm run site:refresh` перед выкатом.

**Как меряется** (замеры на 4 октября 2026). Длина функции — по балансу
фигурных скобок от объявления до закрывающей, строки и комментарии
вычеркнуты; «от объявления до следующего» завышает вдвое (`fmtWhen` значился
48 строк при пяти). «Чистая» — не то же, что «не трогает DOM»: сеть,
хранилище, тосты и `state` DOM не трогают, но в ядре им места нет.

    SHIM["web/api-shim.js<br/>localStorage вместо файла"]
    MOB["mobile/src/<br/>React Native + Zustand"]
    LAND["landing/<br/>статические страницы"]

    CORE --> APP
    CORE -->|"двадцать шесть из двадцати восьми<br/>побайтно"| MOB
    APP --> MAIN
    APP --> SHIM
    MAIN --> DESK["Десктоп<br/>Windows + macOS"]
    SHIM --> WEB["Веб<br/>Vercel"]
    MOB --> ANDROID["Android / iOS<br/>Expo"]
    LAND --> SITE["Лендинг<br/>Vercel"]

    SB[("Supabase<br/>Postgres + RLS")]

    SITE -->|"читает посты блога"| SB

Десктоп и веб делят **один и тот же** `app.js`; отличает их только шим —
третья реализация контракта `window.api`. Телефон делит с ними часть ядра:
DOM там нет, обёртка своя. Десктоп собирается под Windows и macOS вместе и
остаётся одинаковым.

## Общее ядро и где оно кончается

В `src/renderer/core/` двадцать восемь файлов чистой логики без единого
обращения к DOM. На телефон `scripts/sync-mobile-core.js` копирует
**двадцать шесть** из них побайтно, а `tests/unit/mobile-core.test.js` следит,
чтобы копии не разошлись с оригиналом (перевод строки в `core/` прибит к LF в
`.gitattributes`). Копии правятся только этим скриптом, в том же коммите, что
оригинал. Новый файл ядра — `<script>` в обоих `index.html`.

- **Шов — «данные против правил».** Общее — в ядро, различия — параметром
  (`deps`, язык, локаль, «сейчас»). Образец — `core/reports.js`: форма листов
  (строки, колонки, формулы, итоги) общая, подписи и формат — через
  `makeReports()`. Генератор `.xlsx` (`src/xlsx.js`) — на
  `Uint8Array`/`DataView` без `Buffer` и `zlib`, телефон берёт как есть.
- **Миграция** — одна, `core/migrate.js`, правила взяты из обеих сторон (две
  реализации расходились в обе стороны); свои у платформ только поля
  интерфейса — крючок `deps.ui`. Повторный прогон не должен ничего менять —
  самый важный тест приложения.
- **Словари** у платформ разные и останутся разными (экраны разные); общая
  машинка — `translate` и `pluralForm` в `core/lang.js`, там же локали и
  названия языков. Слова закреплены `tests/unit/wording.test.js`: «дедлайн» и
  «вы» (исключение — фразы колоды на «ты»). Каждый ключ — в четырёх языках.
- **Телефон берёт именно функции ядра**: `tests/unit/mobile-parity.test.js`
  сравнивает объекты, а не поведение (проверка поведения пропустила бы
  заново написанную копию), и падает, если у телефона появилась функция с
  именем из ядра вне списков взятых и обёрток.
- **Напоминания списком** (11 октября, `core/reminders.js`): `task.reminders`
  — «до начала» вхождения отрезка, «до дедлайна» (за N мин, ч, дн.), «один
  раз», «повторять» по `repeat.js`. Старые поля (`remindOffsetMin`,
  `remindAt`, `notifiedAt`) — зеркало списка для старых клиентов: читается
  только через `remindersOf`, меняется только через `withReminders` (патч с
  зеркалом). id выведенных напоминаний детерминированные. Движок один:
  `remindersDue` и `markFired` — опрос десктопа, `pendingReminders` —
  расписание телефона, `reminderFeed` — лента.
- **Время работы** (`core/slots.js`): повтор — одно правило у задачи,
  `task.repeat` (12 октября); своего повтора и напоминаний у отрезка нет.
  Пересечения — `slotOverlaps` (18 октября): вопрос, а не запрет.

## Данные

Состояние плоское, живёт целиком в памяти и сохраняется одним куском.

```js
{
  projects: [], tasks: [], statuses: [], tags: [], versions: [], documents: [],
  activeTimer: null,
  ui:       { view, projectId, projectTab, timeMode, timeStatsHidden, navCollapsed },
  settings: { hourlyRate, currency, theme, lang, syncEnabled, syncResolvedFor,
              mode, showTimer, showEarnings, workHours, editor },
}
```

| Сущность    | Чья                  | Почему так                                             |
|-------------|----------------------|--------------------------------------------------------|
| `projects`  | пользователя         | —                                                       |
| `tasks`     | проекта              | у задачи всегда есть `projectId`                        |
| `statuses`  | **проекта**          | раньше были общими; миграция развела их по проектам     |
| `versions`  | **проекта**          | версия принадлежит продукту, а не всему аккаунту        |
| `tags`      | общие **или проекта** | `projectId: null` — общий, виден везде; иначе — только в своём проекте (с 7 октября 2026 заводятся в окне проекта) |
| `sessions`  | задачи               | отрезок времени со своей ставкой на момент записи       |

- **Ставка запоминается в записи времени**, а не берётся из настроек: смена
  ставки задним числом переписала бы весь заработок. Ступени: своя у задачи →
  у проекта (`project.rate`) → общая. У проекта может быть своя валюта
  (`project.currency`); курсов нет, поэтому в общие итоги входят только
  проекты в основной валюте, проект в чужой валюте считается внутри себя
  (`core/money.js`: `effectiveRate`, `moneyScope`, `projectCurrency`).
- Настройки пера и вида редактора (`settings.editor`), режимы и рабочие часы —
  настройки устройства, в синхронизацию не идут.
- **Картинки — не в тексте**: в документе `asset:<id>`, байты — в IndexedDB
  (`lancible-assets`) и копией в Supabase Storage (`supabase/storage.sql`:
  приватная корзина `doc-assets`, папка — id пользователя; PDF и 20 МБ —
  `supabase/storage-pdf.sql`). Пока SQL не выполнен, картинки живут на
  устройстве. При удалении задачи, документа, проекта байты не стираются
  (стирается только аккаунт целиком), поэтому копия держит те же ссылки;
  уборка сирот, если появится, обязана считать ссылки изо всех задач и
  документов.

**Обратная связь** (17 октября): `sb.from('feedback').insert({ id, kind,
text, platform, app_version, lang, device, screenshot_path })` — платформа
`web`/`desktop`/`android`/`ios`, версия (`window.api.getVersion()`: веб —
`version.js` из `package.json`; телефон — `app.json`), язык приложения,
устройство (`navigator.userAgent` до 200 знаков; телефон — «Google Pixel 8 ·
Android 15»). Снимок — в бакет `feedback` по пути `<id>.<тип>` без
перезаписи. id заводит клиент (`fbUuid`; телефон — `uuid4`), один на
попытку и повторы: «Повторить» не создаст второй строки (23505 — уже
дошло) и второго файла.

С 19 октября — **сначала строка, потом снимок**: бакет принимает только
файл, названный в `screenshot_path` строки не старше 15 минут (политика
через `feedback_shot_expected`), путь — строго `<uuid>.<png|jpg|webp>`.
Дошедшая строка второй раз не уходит: отказала только загрузка —
`feedback.shot_failed`, «Повторить» догружает снимок. Частоту держит
триггер `feedback_rate`: с аккаунта 5 за 10 минут и 20 за сутки, гости —
30 в час на всех; отказ `feedback rate` (P0001) — `feedback.rate`, текст
остаётся.

**До Telegram** (19 октября, без Make): строка → триггер `feedback_notify`
(`feedback-bot.sql`, после вставки) → `pg_net` шлёт `{ id }` в Edge Function
`feedback-notify` с ключом `anon` (функция с «Verify JWT») → функция
перечитывает строку служебным ключом и захватывает её одним `update …
where notified_at is null` — повтор вызова дубля не даёт, а из тела кроме
`id` ничего не берётся → отвечает 202 и в фоне (`EdgeRuntime.waitUntil`)
шлёт `sendMessage` (HTML с экранированием, до 4096 знаков; вид, платформа и
версия, язык, устройство, «аккаунт» или «гость», время UTC, короткий id,
текст), потом снимок `sendPhoto` ответом на него. Снимок приходит после
строки — функция берёт его из бакета с повторами (0, 5, 10, 20, 30, 60 с),
не дождалась — отвечает «снимок не загрузился». Не ушло сообщение — захват
снимается (`notified_at = null`), строку можно дослать тем же вызовом.
Секреты — `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` и необязательный
`TELEGRAM_THREAD_ID` (топик в группе с темами; `1` — общий, без номера).

Storage API: прямой `delete` из `storage.objects` файл в хранилище оставил
бы. Сначала файлы, потом строки: не стёрся файл — строка ждёт следующей
уборки. Копии в Telegram команда удаляет руками (Политика §6). Проверка —
`tests/backend/feedback-notify-function.test.js` (без сети, на подменах) и
`tests/unit/supabase-sql.test.js` (текст `feedback-bot.sql`); настройка —
`supabase/functions/README.md`.

## Синхронизация

С 17 октября 2026 (десктоп 0.5.0, веб, телефон 1.3.0) единица
синхронизации — **правка одного поля одной сущности**. До этого уходило всё
состояние одним JSON (`sync_state`): последний прав, офлайн-правки второго
устройства пропадали, вход спрашивал «какие данные оставить».

- **Сервер** — журнал `changes` (`seq` по порядку под замком пользователя,
  `op_id` от устройства, `device_id`, сущность, поле, значение, `at`,
  `base_seq` — докуда устройство видело журнал), ничего не стирает.
  `snapshots` — слепок на `seq` для нового устройства. Realtime — на вставку.
- **Ядро** (`core/oplog.js`): дифф сохранений в правки, слияние по полям,
  конфликты, корзина, слепок, мост. **Конфликт** — две правки одного поля,
  каждая сделана, не видя другую (правки по очереди не спорят): показана
  более поздняя, другая — «Другая версия», в момент слияния ничего не
  спрашивается. Сценарии — `tests/unit/oplog.test.js`.
- **Клиент веба и десктопа** (`app.js`, «Синхронизация — журнал правок»):

```
сохранение   stampSessionIds → commitLocal → данные области вместе с пачкой (sync2)
отправка     upsert(pending → opToRow, on_conflict user_id,op_id, ignore-duplicates) → ackPending
приём        событие realtime / «online» / возврат на вкладку / сверка раз в минуту
             → select seq > lastSeq order by seq (страницами) → commitLocal своего → mergeIncoming
             → глубокая копия состояния пачки в живое → migrate → render → тосты
слепок       lastSeq − seq слепка > 1000 и очередь пуста → compactSnapshot → insert (повтор — 23505, не беда)
первый вход  последний слепок + правки после; слепка нет — sync_state как слепок seq 0 (он же ложится
             в snapshots, если журнал пуст) → bootstrapFromSnapshot → своё и перенесённое — adoptGuestState
```

- **Пачка** (`{pending, lastSeq, conflicts, trash, meta, deferred}`) — полем
  `sync2` в данных области (`lancible:data:<uid>` / `data-<uid>.json`), одной
  записью: данные без своих неотправленных правок были бы потерей. Перекрытая
  своя правка того же поля, ещё не ушедшая, убирается (`coalescePending`).
  Отправленные, но не прочитанные из журнала свои правки — в `meta` (`s`,
  см. ниже).
- **Гость и не связанная с журналом область** пачки не держат: данные уходят
  при первой связи целиком (`adoptGuestState`, `base_seq` 0; общее — по
  полям, расхождение — `conflict`). Перенос «Без аккаунта» в связанный аккаунт
  — сразу, в несвязанный — при связи (совпадение id ждёт в `sync2.adopt`).
- **Телефон** (`lib/sync.js`): тот же порядок шагов на том же ядре; пачка —
  полем `sync2` в записи области, у гостя и несвязанной области `oplog` =
  null; пока своя правка не дошла до журнала, рядом хранится копия
  состояния (после перезапуска дифф вернёт её в очередь). Поводы для чтения —
  realtime, возврат на экран, сверка раз в минуту; повода «сеть появилась»
  нет (NetInfo в приложении нет) — его закрывают повторы. Открытый редактор
  перед приёмом отдаёт текст в стор (`flushEditors`). Подменный сервер тестов
  — `mobile/tests/fakeSupabase.js` по правилам `sync2.sql`.
- **id установки** (`deviceId`) — на устройство, не на область: веб —
  `lancible:device` (`web-<uuid>`), десктоп — `device.json` в папке данных
  (`win-`/`mac-`/`linux-<uuid>`, `src/data-store.js`), телефон —
  `android-`/`ios-<uuid>` (`lancible-device`). По приставке окно конфликта
  говорит, с какого устройства версия.
- **Своя правка — по `op_id`, не по `deviceId`** (19 октября). Один id бывает
  у двух экземпляров: вкладки веба делят `lancible:device`, телефон из
  резервной копии и скопированная папка десктопа уносят свой. Своё — в
  очереди или среди отправленных, но ещё не прочитанных: `ackPending`
  переносит принятое сервером из `pending` в `meta[<сущность>].s` (не больше
  500 на сущность, в слепок не идёт; лежит в `meta`, поэтому клиенты хранят
  его без своих правок). Строка журнала с тем же `deviceId` и чужим `op_id`
  применяется, как чужая; своя — только подтверждается. Своя против строки
  копии в истории поля — по `base_seq`, не «по очереди» (`sawBy`), и копия
  видит спор, как разные устройства; остальные считают правки одного
  `deviceId` идущими по очереди, а показывается у всех последняя из них в
  журнале (`pick`) — итог один. Удаление и возврат у копий решаются по
  очереди `deviceId` у всех. Известный остаток: удаление против правки,
  когда кроме копий в споре участвует третье устройство, — своё удаление
  ложится у себя раньше своего места в журнале, и в редком переплетении
  копии расходятся (генератор в `oplog.test.js`: около 4 историй из 100; без
  удалений — ни одной, это закрыто тестом).
- **Записи времени** заводятся сразу с `id`; без id — ключ `s@<начало>` до
  диффа. **Удалённое** — в корзине 30 дней (`trashSweep` при открытии
  области). Время чужого удаления — `created_at` строки (часы сервера), не
  часы автора: отставшие на месяц часы не выметут удалённое у всех сразу;
  строка без `created_at` — время из правки. Своя поздняя правка спасла
  сущность от удаления старше 7 дней — устройство ставит её в очередь
  заново целиком (`'*'`, время — последней правки сущности, не «сейчас»):
  у остальных корзину могли уже вычистить, и поздняя правка ждала бы у них
  создания. Свежее удаление у всех ещё в корзине, туда правка и вернёт.
- **`\u0000`** в строках правок вычищается при записи в очередь
  (`commitLocal`, выбор версии, возврат из корзины, пометки, гость) и в
  `opToRow` — для очереди, сохранённой раньше: Postgres не берёт его в
  `jsonb`, а вставка очереди — одна транзакция. Состояние пачки — тоже без
  него, дифф считается с очищенной копией.
- **Статусы по умолчанию** — с id от проекта и ключа (`<projectId>:st:<key>`,
  `makeProjectStatuses`, 17 октября): создание на двух устройствах даёт ту же
  сущность; старые случайные id не переименовываются (на них стоят задачи).
- **Документы** — `state.documents`; набор без поля (старый телефон) не
  стирает своё (`core/sync.js: pickDocuments`).
- **Мост к старым клиентам** (десктоп ≤ 0.4.4, телефон ≤ 1.2.3 на
  `sync_state`), один релиз: после слияния (очередь пуста, пауза 1,5 с) новый
  клиент зеркалит состояние в `sync_state` (`updated_by: 'oplog:<deviceId>'`,
  `mirror_seq`); чужая запись без `oplog:` → `legacyBridgeOps(последнее
  зеркало, запись, {at, baseSeq: mirror_seq, stamp: updated_at})` → вставка с
  игнором повторов (id правок от `updated_at` — одинаковые у всех новых
  устройств); зеркало, от которого считал старый клиент, переводит его автор,
  остальные ждут две минуты. Не закрыто: старый клиент, записавший по старому
  состоянию после нового зеркала, победит, как раньше. Мост снимается, когда
  у всех активных установок новые версии.

## Аккаунты на устройстве

17 октября. Правила — `core/accounts.js` (где лежат данные аккаунта, список с
сеансами, план переключения), поведение — `app.js` («Несколько аккаунтов на
устройстве») и `mobile/src/lib/accounts.js`; экраны — `DESIGN.md`,
«Несколько аккаунтов».

- **Область данных** — у каждого аккаунта своя: веб — `lancible:data:<uid>`,
  десктоп — `data-<uid>.json` (`npm run smoke`), телефон — персист-стор
  `Core.mobileDataName(uid)` (`lancible-data` у гостя, `lancible-data:<uid>`);
  переключение на телефоне — `openDataScope(uid)`
  (`persist.setOptions({name})` + `rehydrate()`; пока область не прочитана,
  запись в неё закрыта, иначе пустое состояние легло бы поверх). Гость («Без
  аккаунта») — своя область. Язык и тема новой области — от прежней.
  Переключение не мигает чужим: сохранение молчит, пока область меняется.
  Запись открывает только удачное чтение (19 октября): отказ хранилища или
  битая запись — запись остаётся закрытой, в памяти пусто, а не прежняя
  область, вместо вкладок — ошибка с «Повторить» (`scopeError`). Второе
  переключение, пока идёт первое, — отказ (`switchPending`, строки аккаунтов
  в это время не нажимаются).
- **Список и сеансы**: веб — `lancible:accounts` и сеанс supabase-js в
  `localStorage` (общие у вкладок); телефон — `lancible-accounts` в
  AsyncStorage (`{ list, current, known }`, `known` — вышедшие, чьи данные ещё
  на телефоне); сеанс следующего — `setSession` поверх, к гостю — снятие только
  на телефоне (`_removeSession`), серверный выход — только по «Выйти»,
  `needsSignIn` — только на 4xx сервера. Пачка синхронизации — у области,
  подписка, очередь и повторы — у текущего аккаунта; ответ сети после
  переключения не применяется (`syncFor(uid)`).
- **Две вкладки веба**: область — у вкладки своя. Другая сменила текущего
  (`window.api.onAccountsChanged` → `Core.accountChangedElsewhere`) — эта
  отстала (`scopeStale`): синхронизация, realtime и выгрузка картинок стоят,
  список она не пишет, переключение, вход, «Выйти» и «Удалить данные» не
  идут, пока её не перезагрузят; свои правки ложатся в свою область.
- **Перенос «Без аккаунта»** — первый вход в пустой аккаунт при данных у
  гостя или вручную: `Core.mergeScopeData` (без дублей по id; статусы, версии
  и теги проекта — за проектом), гость пустеет; в аккаунт, связанный с
  журналом, — `Core.adoptGuestState` (см. «Синхронизация»).
- **«Удалить данные с устройства»** у неактивного отзывает его сеанс
  отдельным клиентом без сохранения (`persistSession`/`autoRefreshToken`
  выключены, свой `storageKey`, `setSession` + `signOut({ scope: 'local' })` —
  один POST `/logout`; `revokeAccountSession`). На телефоне вместе с копией
  данных стирается переписка с агентом (`lib/aiKeys.js`, `removeScope`) — с
  устройства и из памяти. Удаление аккаунта на сервере
  уводит его из списка и оставляет копию на устройстве (как обещают
  подтверждение и `landing/delete-account.html`).
- **Картинки заметок** — по аккаунтам: `owner` у записи очереди выгрузки
  (`src/editor/assets.js`), гостевые уходят только переносом (`adoptGuest`;
  на телефоне — сообщение `assets-adopt`, с `ids` — только названные).
  Аккаунт убран с устройства — его записи стирает `forget` (телефон —
  `assets-forget`, ответ `assets-forgotten`; протокол 5, DESIGN.md). Хозяин новой картинки — открытая
  область (`owner: () => scopeUid`; телефон — сообщение `owner`), а не открытое
  облако. Телефон в области вошедшего аккаунта по `ready` редактора и после
  `setContent` шлёт `assets-adopt` с `referenced: true` (гостевые картинки
  открытого документа — этому аккаунту); стирание ждёт открытого редактора в
  очереди `lancible-asset-forget` (`lib/assetForget.js`), снова открытый
  аккаунт с неё снимается. Напоминания телефона
  пересобираются после смены области, облако картинок — только у текущего.

## ИИ-агент

Из свободного текста предлагает задачи, проекты, версии и теги и раскладывает
их по свободному времени. Веб и десктоп — 17 октября (одна панель в
`app.js`), телефон — 18 октября (вкладка «Чат-бот»: `screens/ChatListScreen.js`,
`screens/ChatThreadScreen.js`, `lib/aiChat.js`, `lib/aiAttach.js`); функция и
ядро у всех одни. Экраны — `DESIGN.md`.

```mermaid
flowchart LR
    CORE["core/ai.js<br/>снимок, окна, проверка,<br/>применение, разбор потока"] --> PANEL
    CORE --> CHAT
    PANEL["панель<br/>app.js, веб и десктоп"] -->|"запрос, снимок данных,<br/>токен входа"| FN["Edge Function ai-chat<br/>Supabase"]
    CHAT["вкладка «Чат-бот»<br/>aiChat.js, телефон"] -->|"то же,<br/>fetch из expo/fetch"| FN
    FN -->|"системный промпт, инструменты,<br/>ключ модели"| LLM["Anthropic<br/>API Claude"]
    LLM -->|"поток ответа"| FN
    FN -->|"поток как есть"| PANEL
    FN -->|"поток как есть"| CHAT
    FN -.->|"строка на вызов:<br/>время, модель, токены"| LOG[("ai_calls")]
    FN -.->|"есть ли почта<br/>(до всего остального)"| ACC[("ai_access")]
    PANEL -.->|"rpc ai_has_access"| ACC
    CHAT -.->|"rpc ai_has_access"| ACC
```

- **Агент предлагает, человек подтверждает.** Модель ничего не пишет в
  данные: текст и вызов «предложить изменения», карточку с «Применить» /
  «Отклонить» рисует клиент; применённое отменяется (откат считает ядро).
  Почему: модель путает названия и даты, а молча созданное исправлять тяжелее.
  Операций пять: создать проект, версию, тег, задачу, изменить задачу.
  Удалять, переносить задачу в другой проект и запускать таймер агент не
  умеет — цена ошибки выше пользы.
- **Раскладка — в ядре, агент зовёт её инструментами** `free_windows` и
  `time_spent`: клиент считает ядром (`aiFreeWindows`, `aiTimeSpent`) и зовёт
  функцию снова, не больше четырёх кругов подряд. Рабочие часы — настройка
  устройства (`settings.workHours`, `aiWorkHours`, по умолчанию будни 9–18) —
  только где агент *ищет* время: названные день и час ставятся как есть
  (18 октября), у `free_windows` есть вход `hours`. Пересекаться можно —
  карточка предупреждает (`aiSlotConflicts` поверх `slotOverlaps`).
- **`core/ai.js`** — всё без DOM и сети: снимок (`aiSnapshot` — открытые
  задачи и закрытые за три дня, названия обрезаны, без почт, ставок и
  заметок), окна и время, проверка (`aiValidate`), применение и откат
  (`aiApply`, `aiUndo`), строки карточки (`aiProposalRows`), поток
  (`aiParseSse`, `aiStreamStep`), вложения (`AI_ATTACH`, `aiSniffType`,
  `aiCheckAttachment`/`aiCheckAttachments`, `aiAttachmentBlocks`,
  `aiCompactHistory`), очистка (`aiCleanText`), чаты (`aiChatTitle`,
  `aiChatsNormalize`). «Сейчас» — параметром. `tests/unit/ai.test.js`.
- **Функция `ai-chat`** (`supabase/functions/ai-chat/`): ключ в приложении
  держать нельзя (`anon` открыт). Проверяет вход по токену и доступ по
  приглашению, считает лимит, сама собирает промпт и инструменты (клиент шлёт только переписку и снимок),
  ходит в API Claude потоком и отдаёт как есть с одним своим кадром в начале
  — сколько осталось. `ANTHROPIC_API_KEY`, `AI_MODEL`, `AI_DAILY_LIMIT`,
  `AI_DAILY_UNITS` — секреты функции (смена модели, лимита и бюджета без
  выката приложений). Нет функции (404) — «агент недоступен»; откат — удалить
  функцию.
- **Доступ по приглашению** (21 октября, `supabase/ai-access.sql`): агент
  открыт только аккаунтам, чья подтверждённая почта есть в `ai_access`
  (почта в нижнем регистре, пометка владельца, время выдачи). Выдаёт и
  забирает владелец в Table Editor — без выкладки функции и выката
  приложений. `ai-chat` проверяет это первым после входа — до тела, лимита,
  бюджета, частоты и модели — служебным ключом по почте из `auth.getUser`;
  нет строки, почта не подтверждена, нет таблицы или запрос не прошёл — 403
  `no access`, в журнал не пишется: закрыто по умолчанию. Клиенты узнают то
  же заранее — `rpc('ai_has_access')` (`security definer`, только про
  вызывающего, только `authenticated`) — и вместо поля ввода и чатов
  показывают экран «закрытый тест» с «Запросить доступ»: запрос уходит
  обычной обратной связью с почтой аккаунта. Строка уходит с аккаунтом:
  `delete-account` стирает её до удаления, триггер `ai_access_forget` на
  `auth.users` — при остальных путях. Порядок выкладки и кому выдавать —
  `supabase/functions/README.md`, «ИИ-агент по приглашению».
- **Лимит и журнал**: 50 сообщений в сутки (UTC) на человека; в лимит входит
  вызов, где последнее — слова человека (круг инструментов не тратит). Строка
  в `ai_calls` — до обращения к модели, после потока — токены (всего, из
  кеша и в кеш), цена в единицах, время, причина остановки. Текста переписки
  в базе нет.
- **Бюджет по цене** (19 октября, `supabase/ai-budget.sql`): лимит сообщений
  цену не держит — сообщение с длинной историей, большим снимком и PDF стоит
  как сотня коротких. Цена вызова — `costUnits`: свежий вход × 1, запись в
  кеш × 1,25 (часовая × 2), чтение из кеша × 0,05, выход × 5 (множители
  `UNIT` — цены Sonnet 5.5 у Anthropic). Перед каждым вызовом, и кругом
  инструментов тоже, сумма за сутки UTC сверяется с `AI_DAILY_UNITS` (по
  умолчанию 4 000 000 ≈ $8; расчёт — `supabase/functions/README.md`):
  набралось — 429 `budget` с `retryAfter` до полуночи UTC, модели вызов не
  достаётся. Без колонок `ai-budget.sql` — как раньше, без бюджета.
- **Кеш промпта** (19 октября, `cacheLayout`): префикс у Anthropic —
  инструменты → система → переписка, кеш — побайтное совпадение до точки,
  точек не больше четырёх. Они стоят на системном промпте (вместе с
  инструментами), на снимке, на последнем блоке сообщения человека в этом
  ходе и на конце переписки (в круге — ответ инструмента, в первом вызове
  хода — конец прошлого ответа модели: поиск прежней записи идёт не дальше
  20 блоков назад). Изменчивое — строка `Request` (язык, пояс, «сейчас»),
  `Context.now`, `Context.focus` — из снимка ушло хвостом в сообщение
  человека, после его точки; клиент хвост не хранит, в следующем ходе его
  нет, а всё до точки читается из кеша. Клиент шлёт один снимок и одно
  «сейчас» на весь ход, поэтому круги инструментов читают всё прежнее и
  получают рассуждение модели назад (его подпись помнит префикс). Ломают
  префикс по-прежнему: идущий таймер (`spentMin` растёт), любая правка
  данных, вложения прошлого хода (клиент заменяет их строкой), обрезка
  истории до 40, пауза дольше 5 минут.
- **Данные уходят модели только по действию человека**: снимок — в момент
  отправки, фоновых вызовов нет, без входа — приглашение войти. Переписка —
  только на устройстве, по аккаунту: `lancible:ai:<uid>:chats` и
  `lancible:ai:<uid>:chat:<id>` (телефон — `lancible-ai:<uid>:…` в
  AsyncStorage), ≤ 40 сообщений в чате, с вебом не сходится. Вложения не
  хранятся нигде — только в своём вызове. Политика конфиденциальности
  («ИИ-агент») и `COMPLIANCE.md`.
- **Телефон**: поток — `fetch` из `'expo/fetch'` (в SDK 57 он отдаёт тело
  потоком), применение — действия стора `applyAiProposal`/`undoAiProposal`
  одной правкой с миграцией; перед ними `flushEditors` (`lib/sync.js`) — иначе
  предложение, правящее заметки, затёр бы поздний сброс редактора.
- **Чаты** (18 октября): новый чат — черновик, в список и хранилище попадает
  с первым сообщением, название — `Core.aiChatTitle`; порядок, превью (120
  знаков) и предел 100 чатов — `Core.aiChatsNormalize`; ≤ 40 сообщений для
  модели (`AI_HISTORY_MAX`) и ≤ 120 строк ленты. Старая одиночная история
  (`lancible:ai:<uid>`) при первом чтении становится первым чатом
  (`aiMigrate`: сначала новый ключ, потом удаление старого). Ответ пишется в
  свой чат (`ai.busyChat`), поле в это время недоступно во всех чатах; на
  телефоне другой чат обрывает ответ, уход в список — нет. Ошибки в историю не
  идут. Удалённый чат стирается насовсем; ключи — в Политике cookie.
- **Вложения** (18 октября): скрепка, перетаскивание, Ctrl+V с картинкой
  (веб); «Фото» / «Файл» (телефон: системный выбор файла `File.pickFileAsync`
  из `expo-file-system`, `mobile/src/lib/filePicker.js`; «Файл» — PDF, TXT,
  MD, CSV; с 20 октября вместо `expo-document-picker`, без которого Expo Go
  на iPhone падал на старте). Не больше `AI_ATTACH.maxCount` (4). Тип — по байтам
  (`aiCheckAttachment`: сигнатура и расширение того же вида, «.png» с текстом
  и Word — отказ; больше самого большого предела — отказ без чтения), число и
  сумма — `aiCheckAttachments` после перекодировки. Картинка перекодируется на
  устройстве: длинная сторона ≤ `imageSide` (1568), JPEG `imageQuality`
  (0,85), с прозрачностью — PNG (веб — `aiReencode`: `createImageBitmap` с
  `imageOrientation: 'from-image'`, canvas; телефон — `expo-image-manipulator`
  через `withScaledImage`, PNG — только исходник с альфой в IHDR или `tRNS`,
  HEIC — сначала в JPEG) — уходят EXIF, GPS и хвост после картинки. Текст —
  строгий UTF-8 (`fatal: true`). Отправка — `aiAttachmentBlocks` перед
  текстом; после хода `aiCompactHistory` заменяет вложение строкой «[вложение
  «имя» (тип, размер) — уже разобрано в этом разговоре]», байтов в хранилище
  нет никогда. 400 `bad attachment` (или 413) — «Сервер не принял вложение —
  агенту оно не ушло.», вложение уходит из сообщения, «Повторить» шлёт текст.
  Ошибки — ключи `ai.err_file_*` с пределами из `AI_ATTACH`.
- **Ответы функции в клиенте**: 401 — приглашение войти; 403 `no access` —
  экран «закрытый тест» (прежние версии — общая ошибка сети); 404 — «агент
  недоступен»; 429 `limit` — сутки; 429 `budget` — «На сегодня лимит агента
  исчерпан — он снова заработает завтра.» без «Повторить» (`ai.budget`, счётчик
  сообщений не трогается); 429 `rate` (6 в минуту) — «Подождите N с»,
  «Повторить» — когда время вышло; сеть — «Повторить». Текст ≤ 50 000 знаков.
- **Выкладка мимо `main`**: функция в Supabase. `supabase/ai.sql` — один раз
  до функции, `supabase/ai-access.sql` и своя почта в `ai_access` — до
  функции после 21 октября (иначе агент закрыт и владельцу); `ANTHROPIC_API_KEY` вводит человек; `npx supabase functions
  deploy ai-chat` или Dashboard (`supabase/functions/README.md`). Права и
  ответы без ключа — `tests/backend/ai-chat-function.test.js`; живой вызов —
  только при `LANCIBLE_AI_TEST=1`.

### Безопасность агента

18 октября (круг 20). Агент видит только то, что прислал этот клиент в этом
вызове: снимок своих данных, переписку и вложения. Инструментов три: два
считают на устройстве и ничего не меняют (`free_windows`, `time_spent`),
третий (`propose_changes`) только предлагает — проверяет ядро (`aiValidate`),
применяет человек, отменяет `aiUndo`. Сети, файлов, кода, настроек и чужих
пользователей у него нет: серверных инструментов в запросе нет, источники-
ссылки у вложений функция не пропускает, базу модель не видит. Ключ модели —
только в секретах функции.

**Откуда может прийти атака.**

- *Сам пользователь*: джейлбрейк (сменить роль, вытащить промпт, говорить
  не о деле), трата ключа — много запросов, большие файлы, обход лимита.
- *Любой, кто завёл аккаунт* (регистрация открыта): с 21 октября агент —
  только приглашённым; попытка выдать доступ себе, прочитать список
  приглашённых или занять чужую почту.
- *Содержимое данных*: названия задач, проектов, тегов и версий — свои или
  приехавшие синхронизацией и импортом. Заметки и документы (в том числе
  PDF в редакторе) в снимок не входят.
- *Вложения*: подсказка модели в тексте, PDF или прямо на картинке;
  невидимые символы; файл не того типа под чужим расширением, обрезанный,
  шифрованный; метаданные фото (EXIF, GPS) — уже утечка, а не атака.
- *Подменённый клиент*: свой снимок (огромный, с невидимым текстом), своя
  история — поддельные ответы модели, чужие `tool_use`, вложения «от
  модели», лишние поля блоков (`cache_control`, `citations`, свой `context`
  у документа), ссылки вместо байтов.
- *Повтор и перебор*: частые сообщения и вызовы, которые прикидываются
  кругом инструментов, чтобы не тратить лимит.

**Что может утечь и почему не утекает.** Чужие данные — снимок собирает
клиент из своих, функция читает только `ai_calls` своего `user_id` и строку
`ai_access` своей почты, таблицы под RLS. Ключ — только на сервере, из ответов и ошибок вычищается. Данные в
ссылках (картинка Markdown, уходящая по адресу с данными) — ссылок агент не
выводит (Security), клиенты показывают ответ простым текстом (абзацы и
списки, HTML экранируется, картинок и ссылок нет). Метаданные фото снимает
перекодировка на устройстве. Системный промпт не тайна — он в открытом
репозитории; «не раскрывать» держит агента у дела. Переписка и вложения на
сервере не хранятся; в журнале — время, модель, токены (всего, из кеша и в

**Что остаётся риском.**

- Подсказку из файла или данных модель всё же может послушаться: от
  промпт-инъекции нет полной защиты, текст на картинке очистка не видит. Вред
  ограничен: агент только предлагает, применяет человек.
- Модель может ошибиться в предложении — человек видит карточку,
  подтверждает и может отменить.
- Пользователь может сжечь свой лимит (до 50 сообщений, 250 вызовов и
  `AI_DAILY_UNITS` единиц — ≈ $8 — в сутки); общего потолка на все аккаунты
  нет — расходы держит лимит в консоли Anthropic.
- Лимит и бюджет мягкие: два вызова в одну миллисекунду оба проходят на
  последнем сообщении; цена вызова известна после него, поэтому последний
  вызов дня может перешагнуть бюджет на свою цену. Без `ai-budget.sql`
  бюджета нет вовсе.
- Множители бюджета — цены модели по умолчанию (Sonnet 5.5): с другой
  `AI_MODEL` единица — токен её входа, и у Haiku 5.5 чтение кеша (× 0,1)
  считается вдвое дешевле настоящего.
- Предел тела у шлюза Supabase не документирован: если он ниже 18 МиБ,
  большие вложения получат 413, и `AI_ATTACH.totalBytes` придётся снизить.
- Тяжёлый PDF (больше 100 страниц) отклонит сама модель — человек увидит
  ошибку модели, а не понятное «файл великоват».
- Ответ модели идёт клиенту как есть: от разметки защищает отрисовка
  клиента, а не функция.
- Доступ — по почте, а «Confirm email» в проекте выключен
  (`mailer_autoconfirm`): `email_confirmed_at` ставится при регистрации и
  владения адресом не доказывает. Почту без аккаунта займёт и получит агента
  тот, кто первым на неё зарегистрируется, — доступ выдаётся только почтам
  заведённых аккаунтов (README функций, «Кому выдавать»). То же после смены
  почты: строка остаётся за старой, и новый аккаунт на старый адрес получит
  доступ — при смене почты строку правит владелец.
- Прежние версии клиентов не знают 403 `no access` и показывают общую
  ошибку сети с «Повторить».

## Админ-панель

Решение пользователя 23 октября 2026: только веб, один админ — аккаунт
владельца, отдельный адрес. Это то самое исключение из правила одного
адреса: отдельный проект Vercel с корнем `admin/` —
`lancible-admin.vercel.app`. Сайт статический (HTML, CSS, JS без сборки;
устройство экранов — `DESIGN.md`, «Админ-панель») и ключей не держит: вход —
ключом `anon` и паролем владельца со вторым фактором, а всё, что требует
служебного ключа, делает одна Edge Function `admin`
(`supabase/functions/admin/index.ts`). Таблицы, счётчики и права —
`supabase/admin.sql`.

```mermaid
flowchart LR
    A["admin/<br/>lancible-admin.vercel.app"] -->|"вход: пароль + TOTP (aal2)"| AUTH["Supabase Auth"]
    A -->|"POST { action } + JWT"| FN["Edge Function admin"]
    FN -->|"служебный ключ:<br/>admin_* , таблицы"| DB[("база")]
    FN -->|"письмо-ответ"| RS["Resend"]
    FN -->|"workflow_dispatch,<br/>работы и шаги запусков"| GH["GitHub Actions<br/>publish.yml"]
    CL["веб, десктоп, телефон"] -->|"rpc track_screen"| DB
    AI["ai-chat"] -->|"app_settings, раз в минуту"| DB
    L["лендинг /blog"] -->|"опубликованные blog_posts"| DB
```

**Безопасность.**

- **Кто пускается.** Функция проверяет токен входа (`auth.getUser`), строку
  в `admin_users` (только id аккаунта; почта владельца в репозиторий не
  пишется — свою он вставляет в SQL Editor) и `aal = 'aal2'` в JWT: пароля
  без TOTP мало. Не админ — 403 `forbidden` даже без второго фактора: что
  аккаунт админский, чужой не узнаёт. Нет таблицы — тоже `forbidden`.
- **CORS** — только адрес админки и `http://localhost:5175`; запрос с другим
  `Origin` получает 403 до базы. Служебный ключ — только в секретах функции
  и (локально) в `.env.local`.
- **Счётчики** — функции `public.admin_*`: `security definer` с пустым
  `search_path` (читают `auth.users`, `auth.sessions`), выполнять может
  только `service_role`; у `public`, `anon` и `authenticated` право снято.
  Новые таблицы клиентам закрыты: RLS без политик и `revoke`; читать можно
  только опубликованные посты.
- **Ключи** — только «задан / не задан» (`settings.get`): значения админка
  не видит, в ответы и логи они не попадают. В логах функции — действие и
  коды ошибок, без почт и текста отзывов. Сторожат
  `tests/backend/admin-function.test.js` (функция на подменах, без сети) и
  `tests/unit/supabase-sql.test.js` (текст `admin.sql`).
- **Настройки агента** из админки проходят белый список дважды: при записи
  (функция `admin`) и при чтении (`ai-chat`): модель — из трёх с
  адаптивным рассуждением, усилие — `low`/`medium`/`high`, лимит и бюджет —
  целые в пределах. Списки — копии; совпадение сверяет тест.

**Данные.**

- **Счётчик экранов** (`usage_daily`): день по UTC, аккаунт, имя экрана,
  платформа, число открытий. Шлёт только вошедший с включённым выключателем
  и принятой редакцией — `rpc('track_screen', { p_screen, p_platform })`, не
  чаще раза в 2 с на экран; гость ничего не отправляет. Имя экрана — без
  цифр (`^[a-z][a-z_.-]{0,39}$`, и в check, и в функции): id проекта или
  задачи туда не пролезет. Предел — 2000 открытий на аккаунт в сутки, сверх —
  молча ничего. Хранится 12 месяцев (задание `pg_cron` `usage-sweep`),
  уходит каскадом с аккаунтом.
- **Входы.** В этом проекте запись журнала аудита Auth в базу выключена:
  `auth.audit_log_entries` пуст (23 октября — 0 записей при пяти аккаунтах
  со входами). Поэтому вход — новая сессия в `auth.sessions`: её заводит
  каждый вход паролем или через Google, обновление токена — нет. Сессия, из
  которой вышли, из таблицы уходит, так что число — оценка снизу
  (`logins.source: 'sessions'`). Включат журнал аудита — за день берётся
  большее из записей `login` и новых сессий (`source: 'audit'`).
- **Проекты и задачи «заведено»** — по журналу правок `changes`: создание —
  правка с `field = '*'` (`core/oplog.js`, `diffStates`), первая на
  (аккаунт, сущность); возврат из корзины — тоже `'*'`, но той же сущности,
  и не считается. День — `createdAt` из этой правки, если он есть и не позже
  приёма сервером, иначе время приёма. Только у синхронизирующих аккаунтов
  (десктоп ≥ 0.5.0, телефон ≥ 1.3.0): у статусов `createdAt` нет, у проектов
  и задач — есть у всех правок создания (замер 23 октября).
- **Активные** за день — кто в этот день открыл экран, прислал правку, звал
  агента, оставил отзыв, вошёл или обновил сессию.
- **Ответы на отзывы** — `feedback_replies` (текст, когда и как ушло
  письмо) и `feedback.status` (`new` → `answered` → `closed`; новую строку

  языке отзыва, с исходным отзывом цитатой; у гостя почты нет — ответить
  нельзя. Ответы уходят каскадом вместе с отзывом (удаление аккаунта,
  уборка старше 12 месяцев).
- **Посты лендинга** — `blog_posts` (`title`/`body` на ru и en, как в
  `landing/blog-posts.js`); прежние переносит `supabase/blog-posts-seed.sql`

- **Настройки агента** — `app_settings` (`ai.model`, `ai.effort`,

  (`digest.token`, `supabase/logs.sql`): его читает только
  `work_log_digest`, ни админка, ни `ai-chat` его не отдают.
- **Журнал работы, устройство, граф кода** (23 октября 2026) — разделы
  админки вместо служебных страниц лендинга `/logs`, `/architecture`,
